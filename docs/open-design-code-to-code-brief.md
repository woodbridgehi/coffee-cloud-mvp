3. 先改一组代表性页面：客户总览、平台列表页、手机下单页，检查三者是否属于同一品牌体系，再推广到所有现有页面。

## 四、视觉与排版要求

- 风格：清晰、克制的咖啡设备运营产品。沿用咖啡棕、暖白与中性色基础，建立统一视觉语言；优先可读性和操作效率，不做营销落地页式装饰。
- 三套前端统一组件规范；运营后台允许较高信息密度，消费者页面保留大触控区和简短流程，不强行套相同布局。
- 统一标题层级、正文/说明文字、面包屑或页面定位、筛选栏、操作区、卡片、表格、表单、分页、标签、弹窗、抽屉与通知样式。
- 控制页面宽度和留白，让同级标题、表单标签、卡片与按钮对齐。按钮高度、输入框高度、图标尺寸与标签间距一致，主要操作清楚，危险操作不混同普通操作。
- 金额和数量使用等宽数字，表格数值列右对齐；文本层级清楚，避免大面积过小或低对比文字。
- 长名称、长订单号、超大金额、多位小数、中文与英文混排不得挤压重叠。关键金额和状态不得被截断；需要省略的标识应可查看完整值并按需复制。
- 图表与列表应在内容区正常缩放。手机端使用有标签的卡片或明确的局部横向滚动，不能让整个页面横向溢出。

后台接口实现是当前字段契约的主要依据。`openapi/openapi.json` 是旧快照，尚不包含完整商户接口，不能据此删掉新功能。若发现后端契约缺陷，明确记录原因、受影响页面和修复建议；本次不要自行改 Python、数据库、支付 Provider、鉴权或部署配置，不通过编造前端数据掩盖问题。

重点约束：

1. 区分 `0`、`null`、缺失字段、空列表、加载中、接口失败、权限不足。未知成本显示“待补全”，不能 `value || 0`，不能把异常响应渲染为“暂无数据”。无权限的数据不得仍被渲染在隐藏 DOM、图表或工具提示中。
2. 金额按真实接口单位转换。`*Minor` 是整数分，仅展示时转元，提交时按既有严格校验转回分；精确数量按接口十进制字符串处理，不引入浮点误差。
3. 遵守组织时区；区间界面可含结束当日，但 API 的结束日期是不含当日的右边界。列表、总览、图表、CSV 的筛选、单位和统计口径一致。
4. 实收、退款、净收款、交付确认收入、毛利、经营利润不是同一指标；保留准确名称和解释。正式/测试环境明确区分，不能混算。图表缺失值显示缺口，不能画成零。
5. 支付成功不等于制作成功；退款申请中不等于退款到账；转让待审批不等于转让完成。未知枚举显示明确的未知状态，不能默认显示绿色成功。
6. 字段映射必须与真实 API 对应，尤其订单/设备历史快照、数量、总数、状态与版本。筛选、分页、详情和导出不能错用旧数据；组织切换后不得显示上一个组织的内容。
7. 生产默认真实 API；只有显式 `?demo=1` 才能使用 demo，必须保留明显演示标识。网络失败、没数据或权限不足时绝不自动回退 demo。

## 六、保持现有安全与交互契约

- 客户后台真实配置由 `/api/v1/merchant/auth/config` 提供。当前上线为 USERNAME、mailEnabled=false、limitedRelease=true；用户名3–32位、不区分大小写，密码15–128字符，注册后直接登录，不要求邮箱验证。
- 以服务端 `permissions` 和设备 `allowedActions` 决定显示与可操作性；保留 OWNER / OPERATOR / FINANCE 区分。不得改后端或篡改前端权限表来让所有按钮“可用”。
- 邮件找回/邀请关闭；设备转让、商户收款写入配置、设备命令在当前初版关闭。自动设备成本核算未接通，库存为账面库存。保留准确且适度的能力说明。
- 保留 Cookie 会话、CSRF、同源请求、幂等键、敏感操作重新认证、版本冲突409处理、组织切换时取消旧请求、退出时清理状态。
- 不在浏览器持久化密码、私钥或新增管理员凭据。客户后台与平台后台身份边界必须保持。
- 保留扫码订单访问参数、支付二维码/付款跳转、状态轮询或 SSE、取消订单等既有流程。不得为了视觉测试向实际设备发送命令、付款或退款。
- 所有表单有正确可访问标签、行内错误、提交中的禁用状态；避免重复提交。弹窗支持关闭/取消、Esc、焦点限制与关闭后焦点恢复。图标按钮有名称，状态不能只靠颜色表达。

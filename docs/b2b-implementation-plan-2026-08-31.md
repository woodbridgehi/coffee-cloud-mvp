## 4. 业务边界与权限

组织是客户经营主体，用户是自然人账号，成员关系决定用户在组织内的角色。用户可加入多个组织；设备、门店、订单、成本和收入归组织，不归某个登录用户。

| 角色 | 能力 |
| --- | --- |
| 平台管理员 | 客户组织开通/冻结、出厂设备登记、归属审批、平台审计；与客户会话完全分离 |
| TENANT_OWNER | 本组织全部运营功能，成员邀请和停用、收款账户、成本、退款、设备归属申请 |
| OPERATOR | 授权门店内设备查看与运维、订单查看、库存补货/盘点、经后端授权的安全命令；不能看经营利润、管理成员或收款账户、执行退款和转让 |
| FINANCE | 本组织订单、退款、成本账与报表只读、授权导出；不能执行退款或改配置 |

首期成本采购与费用录入由 OWNER 完成，后续如需财务编辑角色再单独增加，避免同名角色在不同页面权限不同。前端按服务器 `permissions` 显示功能，角色名仅展示；后端每次请求重新验证成员与范围。

门店范围采用 `ALL` 或明确的 store IDs。用户提交的租户 ID、门店 ID、设备 ID 都不是授权凭据。资源不存在与跨租户访问统一返回 404，已知当前组织无操作权限返回 403。

## 5. 数据模型与不变量

### 5.1 身份、组织与设备

- `tenant`：名称、状态、时区、默认币种、数据环境；正式与 INTERNAL_TEST 组织明确区分。
- `user_account`：规范化唯一邮箱、密码摘要、验证时间、状态；不能明文保存密码。
- `tenant_membership`：tenant/user 唯一、角色、状态、门店范围、权限版本。
- `auth_session`：只存高熵会话 token 的摘要、用户、当前成员关系、CSRF 绑定、到期时间、撤销时间、最近重新验证时间。
- `email_action_token`、`invitation`：用途限定、摘要保存、短有效期、单次消费，禁止日志泄露原始 token。
- `store`：tenant、名称、地址、状态；删除为归档且不能丢失历史记录。
- `device_ownership`：设备、tenant、store、有效区间和递增 ownership version。
- `device_claim`：出厂认领凭据摘要及单次使用状态；不同于终端的设备激活码。
- `device_transfer_request`：原组织、目标组织、审批和双方确认状态、阻断原因、归属版本。

终端恢复出厂设置不能改变资产归属。客户不能硬删除设备；退役、归档、解绑申请、转让分别建模。转让前禁止新订单，等待在途生产、退款和人工 HOLD 处理完毕，锁定设备及归属版本后再变更。变更后撤销旧权限、轮换设备凭据、清理旧命令并断开旧连接。原组织历史订单继续归原组织。

### 5.2 交易与支付

订单创建时冻结 `tenant_id`、`store_id`、设备归属版本、商品/配方/价格版本和 `environment`；迁移或改名不重写历史事实。

新增 `payment_account`：tenant、渠道、环境、app ID、商户 ID、密钥引用/加密值、状态、配置版本。每笔支付固定 `payment_account_id` 和配置版本，退款沿原支付账户处理，不随当前默认账户变化。收款推荐客户商户账户直接收款；本期不创建平台钱包、代付或分账结算系统。

对外只返回脱敏配置，私钥不能由 GET 接口回显。正式密钥录入与校验属于后端安全工作，不允许前端调用模拟网关管理 API 来代替它。渠道协议继续沿现有 PaymentProvider 接缝；模拟网关保持独立项目。

新增门店/设备商品售价规则与生效版本，服务端决定最终售价。客户端不传可信结算金额，历史订单价不随新价变动。支付通知按已持久化支付路由验签，不能根据任意 app ID 选一个跨客户账户；保留已有金额核验、重复通知和退款幂等。

### 5.3 成本与经营账

- `material`：单位、单位精度、状态；单位换算由服务端明确处理。
- `purchase` / `purchase_line`：来源、日期、数量、金额、归属门店/仓位、审批/入账状态。
- `inventory_movement`：采购入库、设备补货、实际消耗、损耗、盘点差额、转移；稳定事件 ID 唯一，能关联设备与原始事件。
- `material_cost_version`：移动加权平均成本及有效时点；价格变更不能重算已入账消费成本。
- `expense`：租金、人工、水电、维护、其他；金额、归属、发生日或分摊区间、分摊规则。
- `business_ledger_event`：不可覆盖的收款、退款、收入确认/冲回、直接成本、损耗、支付手续费、费用分摊、调整事实，携带来源与幂等键。
- `daily_operating_summary`：按组织时区/门店/设备/环境聚合，可从事实重建；跨日退款更新实际发生日并保留原交易关联。

金额以整数最小货币单位保存；数量与单位成本用精确定点数。没有成本数据必须标记未知/估算，不默认填零。先用已确认配方标准成本估算时，必须冻结版本并标记 ESTIMATED；后续实际消耗差异通过调整事件表达。

经营口径：

1. 实收 = 支付成功金额；退款 = 退款成功金额，申请中不计入成功退款。
2. 净收款 = 本期实收 − 本期退款，是资金流口径，不等于利润。
3. 营业净收入 = 制作交付确认的收入 − 对应收入冲回；已收款未交付应独立展示。
4. 毛利 = 营业净收入 − 直接材料成本。损耗、支付手续费单列。
5. 经营利润（估算）= 毛利 − 损耗 − 支付手续费 − 分摊运营费用。
6. 不将上述值命名为可提现余额、平台结算款或正式财务净利润；缺项时展示“成本未完整录入”。

收入确认使用后端验证过的生产交付状态，支付失败不能伪造收入，退款不能重复冲减，退款后已经消耗的原料不自动回库。机器转移前后的事实分别保留对应组织快照。

## 6. 安全与隔离实现

- 新客户入口使用独立 `/api/v1/merchant/*`，不复用全局 `/api/v1/admin/*` 授权。平台管理员能力不向客户暴露。
- 同站 HttpOnly/Secure 会话 Cookie，写请求检查 CSRF 与 Origin；密码和邮箱令牌不写浏览器存储。登录限速、统一错误、防枚举、撤销会话、敏感操作重新验证。
- 邮件发送走受控 outbox + 配置好的 SMTP/邮件服务。未配置必须明确不可用，不向浏览器回传验证码充当“已验证邮箱”。演示只能使用隔离测试邮件收件器。
- 应用服务和仓储接收已验证的 tenant context。读取、详情、命令、退款、导出、事件流、后台任务、缓存键和审计全部带归属。
- 数据库租户外键、唯一约束使用正确的 tenant 组合，不能只加筛选字段。共享表启用 RLS；迁移角色与运行角色分离，运行角色不得为超级用户/BYPASSRLS/表所有者。
- 连接池事务使用事务内上下文，离开事务后不遗留租户状态；缺少上下文拒绝访问。公开订单凭据、设备凭据和 worker 各有明确的受限访问路径，不能用全局管理员回退绕过。
- 组织切换、成员停用、权限版本变化后旧请求响应不能留在页面；服务端会话与事件流也必须撤销/重验证。
- 导出为服务器授权的组织数据，避免跨组织缓存与 CSV 公式注入。审计日志记录 actor、tenant、权限范围、资源和关联 ID，脱敏凭据。
